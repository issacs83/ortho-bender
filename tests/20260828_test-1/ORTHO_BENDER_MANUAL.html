Ortho-Bender 사용자 매뉴얼

치과 교정용 와이어 벤딩 머신 Ortho-Bender 를 외부 소프트웨어에서 제어하기 위한 전체 안내서입니다. 장비 기동부터 축 좌표계, 모터 제어, 카메라, CAD/CAM 연동, 안전 규약, 에러 대응까지 실제 작업 순서대로 정리했습니다.

1. 개요

Ortho-Bender 의 소프트웨어 인터페이스는 오직 하나입니다 — i.MX8MP A53 코어에서 구동되는 Python FastAPI 백엔드의 REST API + WebSocket. 그 외의 진입점(직렬 콘솔, 전용 라이브러리, 바이너리 프로토콜)은 애플리케이션 개발자에게 제공되지 않습니다.

1.1 시스템 구성

하드웨어는 SDK 뒤에 완전히 추상화되어 있습니다. 앱 개발자는 스텝 모터 타이밍, SPI 레지스터, GenICam 같은 저수준 세부를 몰라도 됩니다.

1.3 응답 규약 (Envelope)

모든 REST 응답은 동일한 봉투(envelope) 형태를 가집니다.

200 OK — 성공
{ "success": true, "data": { ... }, "error": null, "code": null }
200 OK — 실패 (HTTP 는 여전히 200)
{ "success": false, "data": null,
  "error": "sequence already running",
  "code": "BENDING_BUSY" }
HTTP 상태 코드에 의존하지 마세요 업무 로직 실패는 HTTP 200 + success:false 로 옵니다. 5xx 는 진짜 서버 크래시일 때만, 422 는 스키마 검증 실패(범위 초과 등), 412 는 카메라 오프라인에서 발생합니다. 클라이언트는 항상 success 필드를 먼저 확인해야 합니다.
python — 권장 래퍼
import httpx

class ObError(RuntimeError):
    def __init__(self, code, msg): super().__init__(f"[{code}] {msg}"); self.code = code

def call(client, method, path, **kw):
    r = client.request(method, path, **kw)
    r.raise_for_status()                 # 5xx / 422 는 여기서
    body = r.json()
    if not body.get("success"):          # 업무 실패는 여기서
        raise ObError(body.get("code"), body.get("error"))
    return body["data"]

2.3 첫 명령

  1. 상태 확인 — GET /api/motor/status 로 state 가 0 (IDLE) 인지 본다. 6 (ESTOP) 이면 먼저 POST /api/motor/reset.
  2. 홈잉 — POST /api/motor/home {"axis_mask": 0} 로 센서 장착 축(BEND·LIFT)의 기준점을 잡는다.
  3. 완료 대기 — GET /api/motor/limits 의 homing 이 false 가 될 때까지 폴링.
  4. 이동 — POST /api/motor/move_to {"axis":1,"position":45,"speed":60}.
bash — 위 4단계
BASE=http://192.168.77.2:8000

curl -s $BASE/api/motor/status | python3 -m json.tool

curl -s -X POST $BASE/api/motor/home \
  -H 'Content-Type: application/json' -d '{"axis_mask": 0}'

until curl -s $BASE/api/motor/limits | grep -q '"homing": *false'; do sleep 0.3; done

curl -s -X POST $BASE/api/motor/move_to \
  -H 'Content-Type: application/json' -d '{"axis": 1, "position": 45.0, "speed": 60}'

3.1 축과 좌표계

축마다 단위와 부호가 다릅니다. 이 표를 잘못 읽으면 와이어나 장비가 손상됩니다.

axis이름단위+ 방향원점(datum)리밋 센서
0FEED — 와이어 이송 롤러deg시계방향/zero 로 수동 선언없음 (limit: null)
1BEND — 굽힘 축deg시계방향리밋 센서 호밍있음 (J21 pin11)
2ROTATE — 와이어 회전deg시계방향—벤치 미장착
3LIFT — 수직 이송mm아래(하강)최상단 센서 = 0있음 (J21 pin7)
LIFT 는 + 가 아래입니다 {"axis":3,"position":100} 은 최상단에서 100 mm 하강을 뜻합니다. 일반적인 Z축 관례(위가 +)와 반대이므로 CAD 좌표를 그대로 넘기지 마세요.

axis_mask 비트 — 여러 축을 한 번에 지정할 때 쓰는 비트마스크입니다.

비트0x010x020x040x08
축FEEDBENDROTATELIFT

axis_mask: 0 은 “해당 기능이 가능한 축 전체”를 의미합니다 (예: /home 에서는 센서가 장착된 BEND+LIFT = 0x0A).

더 상세한 축 규약 캘리브레이션 실측값, 이동 한계, 정밀도, 안전 동작의 전체 규약은 장비에 탑재된 06_AXIS_CONVENTIONS.md 에 있습니다 — curl http://<ip>:8000/api/docs/file/sdk/06_AXIS_CONVENTIONS.md (10장).

3.2 모션 상태 머신

GET /api/system/status 의 motion_state, GET /api/motor/status 의 state, /ws/motor 스트림의 state 는 모두 같은 값입니다.

값상태의미새 모션 명령 수락?
0IDLE정지, 명령 대기예
1HOMING리밋 스위치 탐색 중취소(/jog/stop·E-STOP)만
2RUNNING이동 / B-code 시퀀스 실행 중대기열에 적재
3JOGGING수동 조그 중/jog/stop 권장
4STOPPING감속 정지 진행 중아니요

외부 앱의 의무 state == 6 을 감시해 UI 를 잠그고, 사용자가 명시적으로 확인한 뒤에만 /api/motor/reset 을 호출하세요. 하드웨어 E-STOP(M7 GPIO 경로)은 이 API 와 독립적으로 동작합니다.

3.3 이동 명령의 종류

엔드포인트의미거리 상한 처리주 용도
/motor/move_to절대 — 좌표로 이동자동 분할하여 목표에 도달좌표 제어, 외부 앱 권장
/motor/move상대 — 현재 위치에서 만큼상한 초과분은 잘림미세 보정, 스크립트
/motor/jog방향 + 속도 (거리 0 = 연속)—수동 조작
/motor/jog/start·/stop누르고 있는 동안 회전안전 폴백 타임아웃UI 의 ◀/▶ 길게 누르기
외부 앱은 move_to 를 쓰세요 /move 는 1회 명령 상한(FEED·BEND 360, LIFT 240, 이동시간 10 s)을 넘으면 경고 없이 잘립니다. move_to 는 목표에 닿을 때까지 내부적으로 반복 실행합니다 (230 mm LIFT 이동 실측 오차 0.00 mm). 조그는 수동 티칭 전용으로 제한하는 편이 안전합니다.

도달 판정과 감속

  • 가감속은 지정 위치 안에서 완결됩니다 — 45° 를 지령하면 45° 를 지나치지 않고 45° 에 정지합니다.
  • 도달 판정은 2 스텝 이내 (BEND 0.09°, LIFT 0.01 mm).
  • 축이 물리적으로 막히면 로그를 남기고 중단합니다.

3.4 이동 대기열

테스트 벤치는 STEP 신호선을 3축이 공유하므로 한 번에 한 축만 움직입니다.

  • 여러 축에 연속으로 move_to 를 보내면 서로 취소하지 않고 순서대로 실행됩니다.
  • 각 요청은 자기 차례가 끝날 때 응답합니다 — HTTP 요청이 오래 열려 있을 수 있으므로 클라이언트 타임아웃을 넉넉히 잡으세요.
  • 대기 중인 개수는 GET /api/motor/limits 의 queued 로 확인합니다.
  • POST /stop · /estop 은 대기 중인 이동까지 폐기합니다.

3.5 캘리브레이션과 속도 한계

steps_per_unit 은 모든 좌표·속도 변환의 기준이며, 축별 최대 속도는 여기서 자동 산출됩니다.

speed_limit 산출식
speed_limit[axis] = 하드웨어 STEP 상한(8 kHz) ÷ steps_per_unit[axis]

  FEED  200      steps/deg → 40.0   deg/s
  BEND   23.0167 steps/deg → 347.6  deg/s
속도 한계를 하드코딩하지 마세요 캘리브레이션을 바꾸면 speed_limit 도 따라 바뀝니다. 클라이언트는 반드시 GET /api/motor/calibration 의 값을 읽어서 사용하세요. 캘리브레이션은 보드에 영속 저장됩니다(/var/lib/ortho-bender/axis_calibration.json).

3.6 모션 프로파일

축별 가감속 형상과 조그 기본값입니다. GRBL 의 $110-112(최대 속도) / $120-122(가속도), LinuxCNC 의 MAX_ACCELERATION 에 대응합니다.

필드범위의미
jog_speed0–360조그 기본 속도 (deg/s 또는 mm/s). max_speed 를 넘을 수 없음
max_speed0–360축별 기계 속도 한계 — 모든 모션 명령의 speed 가 커맨드 시점에 이 값으로 클램프됨
step_size0–360스텝 조그 1회 이동량
start_hz50–2000램프 시작(플로어) STEP 주파수
accel / decel1–200가감속, 물리 단위(mm/s² 또는 °/s²)
shapelinear · scurve사다리꼴 / 저크 제한 smoothstep
  • accel 은 커맨드 시점에 steps_per_unit 으로 STEP 슬루율(Hz/s, 200–40000 클램프)로 환산되므로, 마이크로스텝이나 캘리브레이션이 바뀌어도 물리적 의미가 유지됩니다.
  • scurve 는 피크 가속도가 accel 설정값과 같아, 전환해도 설정 가속도를 초과하지 않습니다.
  • 감속 램프는 조그 정지/자연 종료에 적용됩니다. 폴트·스톨·E-STOP 은 하드 스톱입니다.
S-curve 의 대가 같은 decel 에서 S-curve 감속은 linear 대비 정지 시간·거리가 1.5배입니다 (피크 가속도를 유지하는 대가). 정밀 정지 위치가 중요하면 linear 를 쓰세요.

프로파일은 /var/lib/ortho-bender/motion_profiles.json 으로 보드에 영속 저장됩니다.

CS=31 로 보드 2장이 소손된 이력이 있습니다 (2026-05-08) cs_max=19 는 그 사고 이후 도입된 하드 가드입니다. 상태 파일을 손으로 고쳐도 로드 시 다시 클램프됩니다. 전원공급기를 바꾸면 반드시 PSU 프리셋도 바꾸세요 — 과대 설정은 하드웨어 손상 이력이 있습니다.

운전 토크와 정지 토크는 별개입니다.

  • run_cs — 축이 움직일 때의 전류. 굽힘축은 토크가 필요하고 피드 롤러는 그렇지 않으므로 축별로 다르게 잡습니다.
  • hold_cs — 유휴 시 코일을 통전 유지해 축이 외력·중력에 밀리지 않게 합니다. 낮출수록 조용·저발열·저토크.
  • 기본값: LIFT·FEED 홀딩 ON, BEND OFF.
상한을 넘는 요청은 거부가 아니라 자동으로 깎입니다 cs_max 이내지만 PSU 캡을 넘는 값은 조용히 클램프되되, 요청값(run_cs)과 실제 적용값(run_cs_effective)이 각각 따로 보고되므로 깎인 축을 설정된 축으로 오해할 수 없습니다. 항상 _effective 를 확인하세요.

6.2 이동

POST/api/motor/move_to 절대 이동 — 권장
request
{ "axis": 1, "position": 5.0, "speed": 8 }
  • position 좌표까지 이동합니다. 단위는 축을 따릅니다(FEED·BEND·ROTATE = deg, LIFT = mm).
  • 긴 이동은 자동 분할됩니다. 1회 펄스는 거리 상한과 10 s 시간 상한에 걸리지만, move_to 는 목표에 닿을 때까지 반복 실행합니다 (230 mm LIFT 이동 실측 오차 0.00 mm).
  • 가감속은 지정 위치 안에서 완결 — 45° 지령 시 45° 를 지나치지 않습니다.
  • 도달 판정: 2 스텝 이내 (BEND 0.09°, LIFT 0.01 mm). 축이 막히면 로그를 남기고 중단.
  • 대기열: 벤치는 STEP 신호선을 3축이 공유하므로 한 번에 한 축만 움직입니다. 연속 호출은 서로 취소하지 않고 순서대로 실행되며, 각 요청은 자기 차례가 끝날 때 응답합니다 (3.4).
POST/api/motor/move 상대 이동
request
{ "axis": 1, "distance": 10.0, "speed": 60.0 }
  • 현재 위치에서 distance 만큼 움직입니다. 좌표로 가려면 /move_to.
  • distance: deg(FEED·BEND·ROTATE) 또는 mm(LIFT). 0 불가, 양수/음수로 방향 지정.
  • speed: deg/s 또는 mm/s, > 0. 커맨드 시점에 max_speed 로 클램프됩니다.
  • 1회 명령 상한을 넘으면 잘립니다 — FEED·BEND 360, LIFT 240, 이동시간 10 s.
잘림은 에러가 아닙니다 상한 초과 /move 는 success:true 로 응답하면서 실제로는 덜 움직입니다. 긴 이동에는 반드시 /move_to 를 쓰세요.

B-code 스텝 모델

한 스텝은 “L 만큼 이송 → β 만큼 회전 → θ 만큼 굽힘” 을 뜻합니다.

필드단위범위의미

스프링백 보상

function subscribe(url, onFrame) {
  let ws, retry = 0, closed = false;
  const open = () => {
    ws = new WebSocket(url);
    ws.onopen    = () => { retry = 0; };
    ws.onmessage = (e) => onFrame(JSON.parse(e.data));
    ws.onclose   = () => {
      if (closed) return;
      retry = Math.min(retry + 1, 6);
      setTimeout(open, 250 * 2 ** retry);   // 지수 백오프
    };
  };
  open();
  return () => { closed = true; ws && ws.close(); };
}

const stop = subscribe("ws://192.168.77.2:8000/ws/motor", (f) => {
  if (f.type === "motor_status") setState(f);
});

if st["motion_state"] in (5, 6):

while (lim := call(c, "GET", "/api/motor/limits"))["homing"]:
    time.sleep(0.2)
if lim["error"]:

print("ready. homed =", lim["homed"])

14.2 증상별 대처

증상가능한 원인확인 · 조치
명령은 성공하는데 축이 움직이지 않음 모터 전원(VMot) 없음 / 드라이버 disable / 폴트 래치 signals.vmot 은 전압 측정이 아니므로 믿지 말 것. driver_enabled, /ws/motor/diag 의 s2ga/s2gb/ot 확인 → /api/motor/reset
이동 거리가 지령보다 짧음 /move 의 1회 상한에 잘림 FEED·BEND 360, LIFT 240, 10 s 상한. /move_to 로 교체
여러 축 명령이 느리게 순차 실행 STEP 신호선 공유 — 정상 동작 /api/motor/limits 의 queued 확인. 클라이언트 타임아웃을 늘릴 것
속도를 올려도 빨라지지 않음 max_speed 또는 speed_limit 클램프 /api/motor/profiles 의 max_speed, /api/motor/calibration 의 speed_limit 확인
정지 위치가 밀림 / 오버슈트 shape:"scurve" 의 긴 감속 거리 정밀 정지가 필요하면 linear 로 전환 (S-curve 는 정지 거리 1.5배)
설정한 전류가 적용되지 않음 PSU 캡에 의해 자동으로 깎임 run_cs 가 아니라 run_cs_effective·cs_actual 을 볼 것. /api/system/psu 프리셋 확인
전류 설정이 422 로 거부됨 cs ≥ 20 또는 ≤ 0 cs_max = 19 는 하드 가드. 우회 불가 (보드 소손 이력)
StallGuard 가 항상 1008 근처 sgt 가 기본값 +63 — 포화 sgt 를 +8 근처로 낮추고 실작업 속도에서 튜닝 (3.8)
SG 가 0 으로 튀며 오탐 sgt 과민 또는 저속 구동 sgt 를 올리고, 저속에서는 SG 를 신뢰하지 말 것
홈잉이 완료되지 않음 센서 미장착 축 지정 / 취소됨 axis_mask 는 0x02(BEND)·0x08(LIFT) 만 유효. limits.error 확인
리밋 가드가 동작 안 하는 것 같음 홈(창 안)에서 출발 — 에지 트리거 특성 정상입니다. 창을 벗어날 때까지 가드가 비활성 (4장)
폴트가 reset 후에도 남음 실제 단락 또는 배선 고장 fault_clear.still_faulted 확인 → 전원을 실제로 내려야 함
E-STOP 후 LIFT 가 내려감 홀딩 토크 해제 — 설계상 동작 기구적 브레이크/스토퍼로 대비. reset 후 재홈잉
WebSocket 이 바로 끊김 /ws/camera 메시지 크기 초과 클라이언트 max_size ≥ 4 MB 설정
카메라가 412 반환 power_state:"off" POST /api/camera/connect (idempotent)
노출을 길게 못 잡음 프레임레이트가 노출 상한을 제한 POST /api/camera/framerate 로 fps 를 낮출 것
ROI 크기가 요청과 다름 드라이버 정렬 단위 보정 (예: 300 → 304) 정상입니다. 응답값을 기준으로 처리
ipc_connected:false Mock 모드이거나 M7 링크 두절 Mock 이면 정상. 실기라면 M7 펌웨어 재기동 → IPC_TIMEOUT 항목 참조
